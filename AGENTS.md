# OpenDoggo Agent Instructions

## Project Boundary

- This is a Java 17/Maven coding-agent harness; production code is under `src/main/java`, while `references/` is staged Python reference material (currently the s06 Subagent lesson: `README.md`/`README.zh.md`/`README.ja.md`, `code.py`, and `references/images/` holding `subagent-overview*.svg`; the s05-era `example/hello.py` and `todo-overview*.svg` were removed when s06 was staged). Each lesson's `code.py` is a standalone per-lesson listing, not cumulative: s06's listing is the s02–s04 base (five tools, permission-as-hook, hook system) plus `task`, and does NOT include s05's `todo_write` — while this Java repo is cumulative, so porting s06 adds `task` as the seventh tool on top of the existing six.
- Implement model interaction, history, tool dispatch, permissions, local execution, termination, and errors in this repository. The assignment forbids agent frameworks/SDKs and API-hosted execution or file tools.
- s02 is complete: `Main` registers all five tools (`bash`, `read_file`, `write_file`, `edit_file`, `glob`). s03 is complete: the three-gate permission pipeline lives in `io.opendoggo.permission`; tools carry no policy. s04 is complete since the v2.0 commit: the hook system lives in `io.opendoggo.hook`. s05 is complete: the sixth tool `todo_write` (backed by `todo.TodoManager`), the AgentLoop reminder counter, and the system-prompt planning sentence. The s06 reference is staged in `references/`; the Java port is complete: the seventh tool `task` (`tool.impl.TaskTool`), a parameterized sub `AgentLoop`, and dedicated sub hooks (see the s06 section).

## Current Architecture

- `Main` loads configuration, wires dependencies, owns the REPL, registers tools in `initTools` (base five via `initBaseTools`, shared with the sub dispatch) and all hooks in `initHooks` plus `initSubHooks` for the subagent, and rolls history back when a turn fails. Since s06 the wiring order is reader → permissionChecker → both hook runners → sub loop → parent dispatch/client/loop, because `TaskTool` needs the assembled sub `AgentLoop` at registration time.
- `AgentLoop` is a silent, UI-free core with constructor `(ModelClient, HookRunner, ToolDispatch)` — no `PermissionChecker` reference and no console output. It appends the complete assistant content before executing tool calls, executes calls in response order, then appends all results as one user message. Preserve this protocol and each `tool_use_id`. Per call it triggers `PreToolUse` before execution — a non-null string becomes `ToolResult(toolCall.id(), blocked)`, execution is skipped, sibling calls still run — and `PostToolUse` after. When a response has no tool calls it triggers `Stop`; a non-null message is appended as a user message and the loop continues. All console output lives in hooks registered by `Main`. Since s06 a second constructor `(client, hooks, dispatch, maxToolRounds, overrunResult, todoReminderEnabled)` parameterizes the round cap (subagents: 30, returning the sentinel string instead of throwing) and the todo nag (off for subagents, whose dispatch has no `todo_write`). Since s05, tool execution is wrapped in try/catch (`Error: {message}` instead of a crash), output is coerced through `String.valueOf`, and a per-run `roundsSinceTodo` counter injects the `<reminder>Update your todos.</reminder>` text block into the third consecutive tool round without `todo_write` (via `Message.toolResults(results, extraText)`).
- `permission.PermissionChecker` is the three-gate pipeline, invoked since v2.0 as the first `PreToolUse` hook (`permissionChecker::check` registered in `Main.initHooks`), not referenced by `AgentLoop`: Gate 1 hard deny list (7 substrings, `bash` only, denied without asking), Gate 2 rules (file tools whose path escapes the workspace; `bash` destructive regex/keywords; `bash` referencing outside-workspace paths — `..` segments, `~`, absolute paths outside the workspace, teaching-grade token heuristic), Gate 3 user approval via the `ApprovalPrompt` callback (default deny). Tools without registered rules pass through — fail-open, matching the reference.
- `tool.impl` file tools (`ReadFileTool`, `WriteFileTool`, `EditFileTool`) resolve paths through package-private `WorkspacePaths.resolveAny`, which resolves relative to the workspace without containment; outside-workspace access is a Gate 2 rule the user may approve.
- `tool.ToolDispatch` is the name-to-`ToolHandler` registry and renders the `tools` array via `toolDefinitions()`. Adding a tool = implement `ToolHandler` and register it in `Main`; no schema edits anywhere else.
- `tool.impl.ShellTool` runs commands in the startup directory with a 120-second timeout and 50,000-character output limit. It carries no policy; dangerous-command checks live in the permission layer.
- `permission.ConsoleApprovalPrompt` implements the `ApprovalPrompt` console UI, sharing the REPL's `BufferedReader` (so two read paths never fight over `System.in`); `Main` wires `new PermissionChecker(workingDirectory, new ConsoleApprovalPrompt(reader))`.
- `model.impl.AnthropicClient` directly implements the Anthropic Messages HTTP/JSON boundary, with the system prompt fixed at construction (wired in `Main`). The root `README.md` is deleted in the working tree (uncommitted); when it existed it documented the tools and permission gates, with an architecture tree that lagged the code.

## s03 — Permission Pipeline (implemented)

- Three gates sit between the model's `tool_use` and dispatch. Historically the loop gained a `check()` call per execution; since v2.0 that check runs as the first `PreToolUse` hook. The tool set and dispatch are unchanged from s02.
- Gate 1 — hard deny list (`rm -rf /`, `sudo`, `shutdown`, `reboot`, `mkfs`, `dd if=`, `> /dev/sda`): substring match, `bash` only, denied immediately without asking.
- Gate 2 — permission rules: file tools whose resolved path escapes the workspace, or `bash` matching a destructive-command regex (`rm`/`del` as standalone command words, so `model` or `echo del x` do not match) or the keywords `rm `, `> /etc/`, `chmod 777`, or `bash` referencing outside-workspace paths (`..` segments, `~`, absolute paths outside the workspace — teaching-grade token heuristic). A hit escalates to Gate 3.
- Gate 3 — user approval via `ApprovalPrompt`: print the reason and the tool call, prompt `Allow? [y/N]`, default deny. The console implementation is `permission.ConsoleApprovalPrompt`, sharing the REPL's reader; `AgentLoop` and the permission layer stay UI-free apart from the Gate 1 block message.
- Denied calls return a `tool_result` carrying the original `tool_use_id` with content `Permission denied by deny list` or `Permission denied by user`.
- Containment moved out of the tools: `WorkspacePaths` only resolves paths (`resolveAny`); outside-workspace access is a Gate 2 rule the user may approve. `ShellTool`'s s02 deny list was removed — policy lives only in `PermissionChecker`.
- Unregistered tools (e.g. `glob`) pass all gates — fail-open, matching the reference.
- The system prompt states "All destructive operations require user approval."
- Since v2.0 this check runs as the first `PreToolUse` hook registered in `Main.initHooks`; see the s04 section below.
- Executable source of truth: `references/code.py`; lesson rationale: `references/README.zh.md`.

## s04 — Hooks (implemented in v2.0)

- Thesis: extensions hang on the loop instead of being written into it — the loop is a stable core that only calls hook mount points, while permissions, logging, and summaries become registered callbacks (lesson title: "挂在循环上，不写进循环里").
- Implemented in `io.opendoggo.hook`: `HookRunner` keeps one ordered list per event (`registerUserPromptSubmit` / `registerPreToolUse` / `registerPostToolUse` / `registerStop`) plus four `@FunctionalInterface` types — `UserPromptSubmitHook.onSubmit(query)` (void), `PreToolUseHook.beforeToolUse(toolCall)` (returns a block reason or null), `PostToolUseHook.afterToolUse(toolCall, output)` (void), `StopHook.onStop(messages)` (returns a continue message or null). `triggerPreToolUse` and `triggerStop` return the first non-null result, short-circuiting the rest; `triggerUserPromptSubmit` and `triggerPostToolUse` notify every hook with return values ignored. There is no JSON decision protocol — the return value alone is the decision.
- Trigger points: `UserPromptSubmit` fires in `Main`'s REPL after the exit-command check, before the query is appended to history; `PreToolUse` in `AgentLoop.run` before `toolDispatch.execute`; `PostToolUse` between execute and appending the result; `Stop` inside the empty-toolCalls branch.
- `Main.initHooks` registers seven hooks in order: UserPromptSubmit context-inject (prints the working dir); PreToolUse 1 permission (`permissionChecker::check`), 2 banner (`[HOOK-PreToolUse]> name`), 3 log (`[HOOK] name(args)`); PostToolUse 1 prints the full tool output between marker lines (the old 200-character preview was removed), 2 large-output warning at >100,000 chars; Stop summary (counts `tool_result` blocks across history, returns null). Order matters: permission before banner/log, so denied calls print nothing.
- Behavior deltas vs the reference that are now settled Java behavior: denial strings are specific ("Permission denied by deny list" / "Permission denied by user"); Gate 1 has 7 entries (the reference has 6 — Java adds `> /dev/sda`); Gate 2 keeps Java's extra bash outside-workspace rule; the `ApprovalPrompt` abstraction replaces the reference's in-hook console prompt.

## s05 — TodoWrite (implemented)

- Thesis: `todo_write` adds planning ability, not execution ability (lesson title "s05: TodoWrite — 没有计划的 Agent，做着做着就偏了"; "没有计划的 agent 走哪算哪"). Long tasks drift because tool results fill the context and dilute the system prompt's influence, so later steps get dropped — a stateful TODO list the model itself updates keeps the plan in view.
- Delta vs s04, component by component: tools 5 → 6 (`+todo_write`); the SYSTEM prompt gains "Before starting any multi-step task, use todo_write to plan your steps. Update status as you go."; `agent_loop` gains a `rounds_since_todo` nag counter and reminder injection. The hook system — all four events, all five hooks — and every numeric limit (120s bash timeout, 50,000-char bash cap, 100,000-char large-output threshold, 200 glob matches, `max_tokens=8000`) are unchanged.
- `TodoManager` (`references/code.py` lines 115–171): in-memory `items` list of `{content, status}` dicts, whole-list replacement on every update (no incremental edits). `update(todos)` parses string input via `json.loads` with an `ast.literal_eval` fallback (never `eval`), then validates: must be a list, at most 20 items, each item an object, `content` non-empty, `status` ∈ {pending, in_progress, completed} (default pending), at most one `in_progress` at a time. On success it replaces `items` and returns `render()` — `[ ]`/`[>]`/`[x]` lines plus a `(done/total completed)` footer, or "No todos.".
- `run_todo_write` wraps `TodoManager.update` in try/except `ValueError` → tool result `Error: {e}` (validation errors go back to the model, not a crash); on success it prints a yellow "## Current Tasks" block to the console and returns the rendered list. The tool rides the ordinary dispatch table with no special-casing; its schema mirrors the runtime limits (`todos` array, maxItems 20, `content` minLength 1, `status` enum).
- The nag reminder is plain loop state, NOT a hook: `agent_loop` tracks `rounds_since_todo`; any round whose tool calls include `todo_write` resets it; on the third consecutive round without one, a `{"type": "text", "text": "<reminder>Update your todos.</reminder>"}` block is appended to that round's results (riding the same user message as the tool_results) and the counter resets.
- Two incidental loop hardenings shipped with s05 — already ported to `AgentLoop.run`: `toolDispatch.execute` is wrapped in try/catch → `Error: {message}` instead of a crash (`ToolDispatch.execute` declares no checked exceptions; ShellTool handles its own `InterruptedException` internally, so one `catch (Exception)` suffices), and the output is coerced through `String.valueOf` so null never reaches `ToolResult`'s non-null `content` constraint.
- `references/example/hello.py` was demo target material for the lesson's try-it prompts (add type hints/docstrings/main guard; create a package under `example/`; fix style issues) — observe whether the first tool call is `todo_write` and statuses progress pending → in_progress → completed. It was removed when the s06 lesson was staged. Next lesson is s06 Subagent (splitting large tasks into independent agents with clean contexts) — see the s06 section below.
- Java implementation: `todo.TodoManager` (validation + render; `IllegalArgumentException` plays the reference's `ValueError`, message strings identical) is owned privately by `tool.impl.TodoWrite`, registered sixth in `Main.initTools`. The reminder counter and `<reminder>` injection live in `AgentLoop.run` (`TODO_REMINDER_THRESHOLD = 3`); the reminder rides the round's results message via `Message.toolResults(results, extraText)` — the protocol-legal text-block rider, deliberately not a fabricated `tool_result` with a fake `tool_use_id` (the API validates tool_use/tool_result pairing). The yellow "## Current Tasks" console print is a `PostToolUse` hook in `Main.initHooks` (the generic full-output hook skips `todo_write`), keeping tools UI-free; it skips `Error:` outputs like the reference. `todo_write` deliberately has no permission rules — in-memory state only, fail-open is the correct posture.

## s06 — Subagent (implemented)

- Thesis: delegation — give a subtask its own conversation context (lesson title "s06: Subagent — 给子任务一段独立上下文"). A subagent starts from a brand-new `messages[]`; only its final text returns to the parent as the `task` tool_result; the intermediate dialogue never enters parent history. What is isolated is messages, not process or filesystem — both loops share the process and the working directory.
- Delta vs s05 in the reference listing: the s06 `code.py` resets to the s04 base (no `todo_write`, no nag counter) and adds five things. (1) `SUB_SYSTEM` (`references/code.py` lines 50–53): "You are a coding agent at {WORKDIR}. Complete the given task, then return a concise final answer." (2) The parent SYSTEM sentence swaps s05's todo sentence for "Use task for focused exploration or a self-contained subtask." (3) `extract_text` (lines 260–267): joins text blocks with newlines — the Java equivalent already exists as `ModelResponse.text()`. (4) `run_subagent` (lines 270–307). (5) `TASK_TOOL` (lines 310–318): name `task`, description "Run a subagent with fresh conversation context and return its final text.", input `{prompt: string, minLength 1}`, required `["prompt"]`; registered like any tool via `TOOLS = [*BASE_TOOLS, TASK_TOOL]` / `"task": run_subagent`. Every numeric limit is unchanged from s05 except the new sub turn cap of 30.
- `run_subagent(prompt)` mechanics: prints magenta `[Subagent started]`; builds `messages = [{"role": "user", "content": prompt}]` (parent history is NOT copied); runs its own loop bounded `for _ in range(30)` with `system=SUB_SYSTEM`, `tools=SUB_TOOLS`, `max_tokens=8000`, appending the full assistant content before executing tool calls — same protocol as the parent. The no-tool-calls branch triggers Stop hooks on the sub's own message list (a non-null force appends as a user message and continues the sub loop — semantics the Java loop already has), then prints `[Subagent done]` and returns `extract_text(...) or "(no summary)"`. Tool rounds execute through the shared `execute_tool` with `SUB_HANDLERS`, so the same PreToolUse/PostToolUse hooks — permission gates including Gate 3 console approval, plus the log hook — police subagent calls; each call also prints a gray indented `[sub] {name}: {first 100 chars}` preview. After 30 turns it prints `[Subagent stopped]` and returns the string "Subagent stopped after 30 turns without a final answer." — a sentinel tool_result, not a crash.
- `SUB_TOOLS = list(BASE_TOOLS)` / `SUB_HANDLERS = dict(BASE_HANDLERS)`: the subagent gets the five base tools and no `task`, so delegation is exactly one level deep. Boundary table from the README: conversation = fresh messages; execution = same process and WORKDIR (filesystem effects are shared); return value = final text only; delegation depth = one level; tool policy = shared hooks (same permission checks for both loops).
- Java mapping / extension points when porting: `AgentLoop.run` already returns the final text and already implements Stop-force-continue, so the sub loop is close to a second `AgentLoop` over a fresh message list — but three reference behaviors need accommodation: (a) the system prompt is baked into `AnthropicClient` at construction (wired in `Main`), while the reference passes `system=` per create call, so the sub needs a second client or a per-call system parameter; (b) `AgentLoop` throws `IllegalStateException` at `MAX_TOOL_ROUNDS = 50`, but the sub wants a 30-round cap that returns the sentinel string; (c) `ToolDispatch` has no restricted view, so the natural port is a second `ToolDispatch` registering only the sub's handlers.
- Java implementation: `tool.impl.TaskTool` (seventh tool, registered in `Main.initTools`) wraps a sub `AgentLoop` over a fresh per-call `ArrayList<Message>`; `TaskTool.STOPPED_MESSAGE` is the overrun sentinel. `AgentLoop` gained a second constructor `(client, hooks, dispatch, maxToolRounds, overrunResult, todoReminderEnabled)` — the parent keeps the 3-arg default (50 rounds, throw, nag on); the sub passes `(30, TaskTool.STOPPED_MESSAGE, false)`, so overrun returns the sentinel string as a normal tool_result and the todo nag is suppressed (the sub dispatch has no `todo_write`). The sub client is a second `AnthropicClient` (SUB_SYSTEM + the five base tool definitions); `initBaseTools` registers one set of five tool instances into both dispatch tables. Settled decisions: the sub tool set is strictly the five base tools (reference posture); sub display runs on its own `HookRunner` from `Main.initSubHooks` — the same `permissionChecker::check` instance (policy identical, delegation does not downgrade permissions) plus a `[sub] name: 100-char` PostToolUse preview and a `[sub] Stop` summary, deliberately without the parent's banner/log/full-output dump (a settled Java delta vs the reference's fully shared hook list, avoiding double printing); `[Subagent started]` is the parent's 4th PreToolUse hook and `[Subagent done]`/`[Subagent stopped]` the 4th PostToolUse hook (stopped chosen by comparing output to `TaskTool.STOPPED_MESSAGE`); `task` itself carries no permission rules — fail-open like `todo_write`, inner calls still gated. The parent SYSTEM keeps the s05 todo sentence and adds the task sentence (cumulative).
- Try-it prompts from the README: use a subtask to find what testing framework the project uses; delegate reading the `.py` files and summarizing what each does; use a task to create `example/string_tools.py` with `slugify(text)`, then verify from the parent. `references/example/` no longer exists (removed with the s05 material) — recreate target material when porting or demoing. Next lesson is s07 Skill Loading (inject knowledge on demand instead of stuffing the system prompt).

## Commands

- Compile after source changes: `mvn compile`.
- Run tests: `mvn test`. There are currently no files under `src/test`. If JUnit 5 tests are added later, declare maven-surefire-plugin 3.x in the pom first — Maven 3.8's default surefire 2.12.4 silently discovers no JUnit 5 tests.
- Build the executable shaded JAR: `mvn package`; run it with `java -jar target/opendoggo-0.1.0-SNAPSHOT.jar`.
- For development, generate `cp.txt` once with `mvn org.apache.maven.plugins:maven-dependency-plugin:3.6.1:build-classpath -Dmdep.outputFile=cp.txt`, then run `java -cp "target/classes:$(cat cp.txt)" io.opendoggo.Main`.
- Self-running s05 demo (no API key, scripted `ModelClient` drives the real loop/tools/hooks and self-checks the reminder): `java -cp "target/classes:$(cat cp.txt)" io.opendoggo.demo.TodoDemo` after `mvn compile`.

## Configuration and Safety

- `.env` values override process environment values. Keep `ANTHROPIC_API_KEY` only in the process environment; never read, print, edit, or commit credentials.
- The startup directory is the agent workspace, and shell children inherit environment variables. Deny-list and permission-rule checks are teaching-grade substring matching, not a security boundary.
- Do not edit generated/local files: `target/`, `cp.txt`, or `dependency-reduced-pom.xml`.
